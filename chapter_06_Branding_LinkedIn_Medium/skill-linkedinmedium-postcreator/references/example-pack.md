## Medium article

**Title:** Manual Tester to Automation in 90 Days: The 7-Step Formula That Works

**Subtitle:** 2027 is the last year "manual-only" works as a career plan. Here are the exact 90 days I'd give anyone starting tomorrow.

**Tags:** Software Testing, Test Automation, Playwright, TypeScript, Career Change

---

2027 is your last year as a manual tester. Unless you start coding in the next 90 days.

That line is meant to sting. Manual testing skills still matter. Knowing what to test, where users break things, and when a release isn't ready is judgment no script replaces. But the job title built only on running test cases by hand is shrinking. The testers keeping their seats are the ones who can turn that judgment into code that runs on every build.

The good news: the gap is smaller than it looks from the manual side. It takes a plan, an hour a day, and a few hundred reps.

### I started manual too

My first QA project was fully manual. I tested end-to-end ad campaign workflows and validated data for an ad-tech client, in a high-volume environment where a wrong budget allocation meant real money going to the wrong place.

Today I maintain a hybrid Playwright framework for an enterprise Salesforce platform. It took full regression from 5 days to 3 hours. At a UK healthcare client, I went through a 100+ case manual regression suite, picked 70 high-value automation candidates, and cut manual regression effort by 80%.

Both jobs taught me the same thing. The switch is not a talent. It is a schedule.

### Why most manual testers stall

Most people who try to switch don't fail because coding is too hard. They fail in one of three ways.

They hop between tools. Selenium this month, Cypress the next, a Python course after that. Nothing compounds, so month three feels like day one.

They watch instead of type. They put in hours of video and minutes of code, so the fear of the editor stays exactly where it was.

They leave no proof. They learn things, but there is nothing a hiring manager can open and check.

The seven steps below are built to close all three gaps.

### The 7-step formula

**1. Pick one roadmap and stop hopping.**
Choose TypeScript with Playwright and commit to it for 90 days. Playwright gives you a test runner, assertions, API testing, parallel runs and a trace viewer in one tool. That means you aren't stitching five libraries together while you learn. TypeScript is JavaScript with types, so every JavaScript exercise you do still counts.

**2. Be 100% clear on your topics for the next 3 months.**
Write the list before day one and pin it. Don't add to it until month three ends.

| Month | Focus | Topics |
|---|---|---|
| 1 | The language | Variables and types, functions, arrays and objects, loops, async/await and promises, modules, TypeScript basics |
| 2 | Playwright core | Locators (getByRole, getByLabel, getByText), web-first assertions, fixtures and hooks, API testing, debugging with the trace viewer |
| 3 | The framework | Page Object Model, environment config, test data, parallel runs, HTML reports, running the suite in CI (GitHub Actions or Jenkins) |

**3. Know the skills and the time.**
Give it one focused hour a day, every day, for 90 days. That adds up to roughly 90 hours. Treat that hour like a release window: same time daily, notifications off, no rescheduling. Daily consistency beats weekend marathons, because the goal is to make code feel ordinary.

**4. Do the reps: 300–400 exercises.**
Ten small exercises a day in month one gets you to 300. Add around 100 more alongside Playwright in month two. Keep them small and test-flavoured. For example, filter an array of test results by status, parse a JSON API response, write an async function that retries until a condition is true, or compare two objects field by field.

This is the step that removes the coding fear. Not a certificate, not another course. Confidence builds quietly, a few exercises at a time, until one day the editor stops feeling like someone else's territory.

**5. Automate the test cases you already run.**
This is your unfair advantage. Beginners in automation guess what is worth testing. You already know. Take 10 manual test cases you could run in your sleep and turn each one into a Playwright test.

That is how I approached the healthcare suite. I didn't try to automate everything. I picked the cases where automation paid back first.

A manual case like this:

```
TC-014: Login with valid credentials
1. Open the login page
2. Enter a valid email and password
3. Click "Sign in"
Expected: the dashboard shows "Welcome back"
```

becomes this:

```ts
import { test, expect } from '@playwright/test';

// baseURL is set in playwright.config.ts
test('TC-014: login with valid credentials', async ({ page }) => {
  await page.goto('/login');
  await page.getByLabel('Email').fill(process.env.TEST_USER_EMAIL!);
  await page.getByLabel('Password').fill(process.env.TEST_USER_PASSWORD!);
  await page.getByRole('button', { name: 'Sign in' }).click();
  await expect(page.getByRole('heading', { name: 'Welcome back' })).toBeVisible();
});
```

Every line maps to a step you already wrote. You are not learning testing from scratch. You are learning to write down what you already know in a language a machine can run.

**6. Build 4–5 projects, including one real framework.**
Exercises teach syntax. Projects teach structure. A solid set looks like this:

- A UI suite against a public demo store that covers login, search, cart and checkout.
- An API suite using Playwright's request context, with create, read, update, delete and negative cases.
- A data-driven suite that reads test data from JSON and runs the same flow with many inputs.
- One end-to-end framework with page objects, fixtures, environment config, HTML reports and a CI pipeline that runs on every push.
- Optionally, your step-5 test cases rebuilt against a public app.

At least 3–4 of these should be public on GitHub.

**7. Put it on GitHub and build in public.**
Give every repo a README that says what it tests, how to run it, and shows a screenshot of the report. Then post on LinkedIn every week about what you built, what broke, and how you fixed it. A GitHub link is proof a resume line can't give. Weekly posts turn 90 days of quiet work into a reputation.

One rule outranks everything here: never push your employer's code, URLs or test data. Rebuild the idea on a public app instead.

### What I'd do if I started tomorrow

- Install Node.js, VS Code and Playwright today with `npm init playwright@latest`.
- Write your three-month topic list on one page and pin it above your desk.
- Block one hour on your calendar, every day, for the next 90 days.
- Do your first 10 exercises tonight, not Monday.
- Pick the 10 manual test cases you know best. They are your first automation backlog.
- Create your GitHub repo on day one, even while it's empty.

> Automation doesn't replace judgment. It buys you time to use it.
